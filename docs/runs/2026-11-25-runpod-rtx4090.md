# Real weights on RunPod — 2026-11-25

FastWan 2.1 T2V 1.3B (`FastVideo/FastWan2.1-T2V-1.3B-Diffusers`, f32 shards) and
`taew2_1.safetensors`, exported and run on a RunPod pod: RTX 4090 24 GB, 32 vCPU,
124 GB RAM, Ubuntu 24.04, NVIDIA driver 595.112.07. Software: litert-torch 0.8.0,
ai-edge-litert 2.1.2, torch 2.9.1+cu128, jax 0.8.2 (CPU). The pod was driven with
`h3-litert/scripts/runpod/{pod,remote}.py`; every number below is from `out-N.log` of
that session.

## Prompt encoding

`fastwan-litert encode --model-dir /root/work/fastwan` (UMT5-XXL, transformers 5, GPU):
7.8 s per prompt including the 11 GB load; `[512, 4096]` embeddings, 33 / 34 real tokens.

## Export

| export | graphs | size on disk | wall (`--jobs 6`) |
|---|---|---|---|
| dyn-int8 (the old `--weights f16`, see below), both tiers | 98 | 1 502 MB | 68 s |
| f32, size 480x272x33 | 96 | 5 716 MB | 68 s |
| f16 (fixed), both tiers | 98 | 2 913 MB | 380 s (6 workers, beside the H3 export and a parity run) |

Per block (kv + qkv + post): 1.2 + 1.7 + 4.7 s in a worker; six workers convert the 30
blocks in ~50 s. The first six `kv` conversions take 5.7 s (one-time converter warm-up per
process). Peak RSS per worker stayed under 3 GB — the per-block loader never holds the whole
DiT.

## Parity against the uncut PyTorch model (`python/scripts/parity_real.py`)

480x272x33, seed 7, the fox prompt, CPU interpreter, 3 DMD steps.

| graphs | per-forward velocity rel. error (steps 1–3) | latent rel. error after 3 steps | TAE decode vs torch (8-bit, max / mean) | end-to-end frame mean abs (8-bit) |
|---|---|---|---|---|
| f32 | < 5e-5, < 5e-5, < 5e-5 | 8.7e-5 | 1 / 4e-5 | 0.0036 |
| dyn-int8 | 0.046, 0.037, 0.027 | 0.20 | 57 / 0.89 | 8.4 |
| f16 (fixed) | 7e-4, 1.0e-3, 5e-4 | 6.6e-3 | 1 / 0.012 | 0.19 |

The f32 graphs reproduce the PyTorch model to float rounding: the graph cut (row chunks,
padded rows, query-chunked attention, the TAEHV chunk memories) is exact at real width.

**The `--weights f16` export was not f16.** The first parity run showed 4.6 % per forward,
while the PyTorch model with every weight rounded to f16 differs from itself by 0.06 %
(`bf16`: 0.74 %) — so the error was not weight rounding. The same graph from the f16 and
the f32 export differed by 1.3–1.7 % on XNNPACK *and* on the reference kernels, and the
"f16" files held `int8` tensors and no `float16` ones: the exporter passed the converter
flag as a dotted key (`"target_spec.supported_types"`), which litert-torch set as a stray
attribute, and `Optimize.DEFAULT` alone writes **dynamic-range int8** (int8 weights,
activations quantized per row at run time — hence 1.5 GB for 1.3B parameters). Both
exporters now pass the nested form; the tiny fixture at f16 moved from ~1e-2 to 5e-4,
and the real-weights rows above are the fixed export. The dyn-int8 rows stay here because
they are a useful data point: the clip is visibly the same fox.

## Generation

| graphs | accelerator | size | prepare | per step | denoise | decode | peak host RSS |
|---|---|---|---|---|---|---|---|
| dyn-int8 | CPU (XNNPACK, 32 threads), pod otherwise idle | 480x272x33 | 0.3 s | 31.0 s | 93.0 s | 1.5 s | 3.4 GB |
| f16 | CPU, pod shared with the H3 export and the 832 run | 480x272x33 | 0.4 s | ~190 s | 563 s | 10.6 s | — |
| f16 | CPU, pod idle, raw-interpreter runtime | 480x272x33 | 0.4 s | 47.7–48.3 s | 143.8 s | 2.6 s | — |
| f16 | CPU, pod idle, raw-interpreter runtime | 832x480x81 (32 760 tokens) | 0.5 s | 2 466–2 469 s | 7 403 s (2 h 3 min) | 18.3 s | 2.5 GB (decode) |

The 832x480x81 tier is attention-bound on a CPU: the row graphs scale 7× from the small
tier (~340 s of the step), the rest is the dense attention graph — 30 blocks × 128 query
chunks of a `[256 × 32 760]` 12-head attention, ~51 GFLOP per call, at ~0.1 TFLOPS through
TFLite's batch-matmul + softmax kernels. A first attempt on the previous runtime, which
re-copied the 2 × 200 MB K / V inputs into the graph for every query chunk, was stopped after
2.5 h without finishing a step; the raw-interpreter runtime skips the copy when the array is
the same object as last call. On a GPU the same graph is the part that gains the most; on a
CPU a key-chunked (flash-style) attention graph is the next thing to export.

f16 is slower than dyn-int8 on this CPU (48 s vs 31 s per step): the f16 constants are
unpacked to f32 and repacked by XNNPACK every time a block graph is opened, and with
`--resident 4` of 30 blocks that happens each step; dyn-int8 graphs pack once and run int8
kernels. The uncut PyTorch model takes 86 s for the same three steps on the same cores.

## GPU accelerator notes (ai-edge-litert 2.1.2 on Linux)

**No LiteRT graph ran on the RTX 4090 in this session.** The Python package's only GPU
accelerator on Linux is the WebGPU one (Dawn over Vulkan; `libLiteRtGpuAccelerator.so`,
`libLiteRtOpenClAccelerator.so` and `libLiteRtVulkanAccelerator.so` are looked for but do not
register). The pod's container has the CUDA libraries (the UMT5 prompt encoder used the card)
and an OpenCL ICD (`clinfo` lists the GPU), but its NVIDIA Vulkan ICD does not load
(`vkCreateInstance` not found in `libGLX_nvidia.so.0`), so the only Vulkan device is
`llvmpipe`, a CPU rasterizer. `--accelerator gpu` therefore "compiled" and ran graphs on
llvmpipe: 0 % GPU utilisation, 4 MiB of GPU memory, ~5 s per block chunk — stopped and not
reported as GPU numbers. Moving the WebGPU library aside leaves no GPU accelerator at all.

What the run did fix or learn on that path:

- `TensorBuffer.read` needs the element count, which `CompiledModel` does not expose for
  outputs; the runtime takes the output shapes from a metadata-only interpreter.
- A graph the accelerator refuses now falls back to the CPU interpreter per graph instead of
  failing the run (`Graph` warns once per file).
- The WebGPU backend compiled every f32 graph and every true-f16 graph of the tiny fixture; it
  refused the dyn-int8 `post` graph (dynamic-range int8 is not a GPU format). The web runtime
  (LiteRT.js, WebGPU) is where these graphs meet a real GPU; the pod could not stand in for it.
- The Python `TensorBuffer.write/read` go through Python lists in this release, so even with a
  working Vulkan driver the desktop GPU numbers would be host-copy bound.

## What was not run

- Any LiteRT graph on the GPU (see above): the Android / iOS / web runtimes against these
  graphs need a device or a browser; they pass the tiny fixture in CI and read the same
  manifest.
- int8 / int4 weight-only exports at real weights (the quantizer path is covered by the tiny
  fixture only).
- 832x480x81 at f32, and any size beyond the two tiers of the manifest.
